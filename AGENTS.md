# AGENTS.md

Angular 22 standalone-component SPA ("Compliance Portal") generated by Infragistics App Builder / Ignite UI CLI, backed by a **Spring Boot + PostgreSQL** API in `backend/`.

## Commands
- `npm start` / `npm run build` — dev server / production build
- `npm test` — runs unit tests (`ng test --watch=false`)
- `npm run lint` — eslint (TS + HTML templates)
- `mvn -f backend/pom.xml clean package` — rebuild the API jar (see "Backend" below)

Angular CLI is used directly via npm scripts.

`README.md` documents the **portable distribution bundle**; the dev workflow for this checkout is in `DEVELOPMENT.md`, and `HANDOFF.md` is the full onboarding/architecture/schema reference for whoever receives the repo as a zip.

## Testing (Vitest, NOT Karma)
- Tests use the **Vitest** runner via `@angular/build:unit-test` (`runner: vitest`), with `happy-dom` as the DOM environment. Do not reintroduce Karma.
- Focused run of one suite: `npx ng test --watch=false --include='src/app/admin-view/admin-view.component.spec.ts'`
- Spec files use `TestBed.configureTestingModule`; globals come from `vitest/globals` (types in `tsconfig.spec.json`).
- `ComplianceRepositoryService` is an `HttpClient` wrapper, so specs must provide a fake. Use `createRepositoryFake()` from `src/app/testing/compliance-repository.fake.ts` rather than hand-rolling a `useValue` object. It also exports `flush()`, `namedDocument()` and `applicationWithCompleteFollowUp()`.
- `tsconfig.spec.json` explicitly includes `src/app/testing/**/*.ts`, since the default `include` only covers `*.spec.ts`.

## Architecture
- Standalone components throughout; no `NgModule`s. Root bootstrap via `bootstrapApplication` (`src/main.ts`), routing from `src/app/app.config.ts` + `app.routes.ts`.
- **Two separate routed views, one per URL** — there is no mode toggle and no `switchMode()` any more:
  - `ClientViewComponent` (`src/app/client-view/`) → `/solicitud` (blank form) and `/solicitud/:id` (loads that application via `ActivatedRoute.paramMap`; after the first successful submit the component navigates to `/solicitud/<id>` with `replaceUrl`).
  - `AdminViewComponent` (`src/app/admin-view/`) → `/admin`. Bandeja / Histórico remain **internal tabs** on the `adminTab` field, not child routes.
  - `/master-view` is kept only as a redirect to `/solicitud` for old bookmarks.
- Field catalogs, Spanish labels, status labels and document-grouping helpers are shared pure functions in `src/app/shared/compliance-fields.ts`. Both components hold thin one-line delegates so templates call `documentLabel(x)` / `getStatusLabel(x)` as before. **Add new fields there, not in a component.**
- `ComplianceRepositoryService` (`src/app/compliance-repository.service.ts`) is a thin `HttpClient` wrapper over `environment.apiUrl`. IDs come from `crypto.randomUUID()`.
- `getAll()` returns **lossy list rows** (no documents, blanked detail fields), so the admin view must call `getById()` on selection — that is what `loadingDetail` and the stale-response guard in `selectApplication()` exist for.
- Domain types + statuses (`NOT_APPROVED | PENDING | APPROVED | REJECTED`) in `src/app/compliance.models.ts`. Approval rule is `canApprove()`: base docs reviewed AND (follow-up forms disabled OR submitted).
- UI copy is in Spanish (es-BO locale used in reports); keep new user-facing strings in Spanish.

## Backend
- Spring Boot in `backend/`, JDBC via `JdbcTemplate` (`ClientRepository`), Flyway migrations in `backend/src/main/resources/db/migration/`. Postgres connection comes from `application.yml` (`DB_URL` / `DB_USER` / `DB_PASSWORD`, defaulting to `compliance` on `127.0.0.1:5432`).
- PDF reports are generated **server-side** in `pdf/PdfService.java`; the client just POSTs to generate and `window.open`s the download URL. There is no hand-built PDF byte stream in the frontend.
- Dev workflow is: `mvn -f backend/pom.xml clean package`, then `java -jar backend\target\compliance-backend-0.1.0.jar`. Flyway applies pending migrations at boot, so a new migration only takes effect after that rebuild + restart. `mvn clean` fails with "Failed to delete ...\compliance-backend-0.1.0.jar" if a backend is still running — stop the JVM first.
- `start.ps1` / `stop.ps1` are for the **portable distribution bundle**, not this checkout. They expect `pg\pgsql\bin\initdb.exe`, `pgdata\`, `frontend\` and `backend\compliance-backend-0.1.0.jar` — **none of which exist here** (this repo has the Angular app at the repo root and the runnable jar at `backend\target\`), so `start.ps1` will abort in this directory. It also aborts if port 5432 is already taken, which it is by the system PostgreSQL. Use the manual `mvn` + `java -jar` flow above while developing.
- `backend\target\compliance-backend-0.1.0.jar` is the only runnable jar (~25 MB, Spring Boot repackaged). The 112 KB `cumplimiento.jar` at the repo root was a stale pre-Spring-Boot artifact and has been deleted; don't re-add it.
- **Never edit an existing migration** — Flyway validates checksums and the app will refuse to start. Add a new `V<n>__name.sql`.
- All string columns are bounded `varchar` (migrated in `V3__varchar_lengths.sql`); there is no `text` left. The widths are deliberate: `documents.file_name` stores the document's Spanish display label (up to 46 chars), and `clients.rejection_fields` stores a JSON array of flagged form keys (up to 329 chars when all 18 are selected) — neither can be as short as 25. `documents.form_key` is `varchar(25)` and the longest key in the app is `representativeDocument` at 23 chars, so a longer new field key will start failing inserts.

## Conventions & gotchas
- Templates use SCSS (`inlineStyleLanguage: scss`); component style extension is `.scss`. The shared shell/typography/form-primitive styles live in the global `src/styles/_shared.scss` (`@use`d from `src/styles.scss`); each view component owns only its branch styles, which keeps both under the 16 kB `anyComponentStyle` budget in `angular.json`.
- Selector prefixes: component `app` (kebab-case), directive `app` (camelCase) — enforced by ESLint.
- `tsconfig.json` sets `strict`, `strictTemplates`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns` — respect these; the linter relaxes `no-explicit-any` and `prefer-inject`.
- The app has **no authentication**. `/admin` exposes every client, and `/solicitud/:id` will load any application whose id you have. Treat both as demo-only until auth is added.
- `npm install` before first build/test if `node_modules` is missing.
